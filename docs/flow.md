# ROGUEON — Backend Flow (Admin, Website, POS)

Companion to `updatedprd.md`. This document walks through the actual request-by-request flow for each surface.

---

## 0. Guest vs. Logged-in — How the Backend Tells Them Apart

This is not "sessionId vs JWT" — it's two entirely different mechanisms:

- **Guest tracking** — a random ID stored in a cookie (e.g. `guest_session_id`), generated by our own code, not Better Auth. It has no `userId` behind it at all — it's purely a way to recognize the same anonymous visitor across requests, so their cart persists on refresh. Not an authentication mechanism.
- **Logged-in tracking** — Better Auth's own session cookie, created at login, tied to a real `userId` in the `Session` table. This is a genuine authenticated session.

**On every request, the backend checks in this order:**
1. Is there a valid Better Auth session cookie? → yes: this is a logged-in user, use `session.user.id` and `session.user.role`.
2. No valid Better Auth session? → check for our own guest cookie. If missing, generate one now and set it. Use it only to look up/create their guest `cart`.

A guest never has a `userId` anywhere in their request context — only a `sessionId` used strictly for cart lookup.

## 1. Admin Flow

### 1.1 Staff account creation
- Admin (already logged in, `role: admin`) calls a staff-creation endpoint, providing name, email, and an initial password (or triggers a "set password" email — either is viable, admin's choice).
- Internally, this still goes through Better Auth's signup logic — creates a `User` row (`role: cashier` or `role: admin`) and an `Account` row (password hash) — just triggered by admin, not self-serve signup.
- Staff can now log in through the same shared `/auth/login` endpoint as everyone else; role determines what they can access afterward.

### 1.2 Category & product management
- Admin creates categories (with optional `parentId` for nesting).
- Admin creates a product (name, description, images, category, status) — no stock yet, since stock lives on variants.
- Admin creates one or more variants for that product (size, color, SKU, price, initial `stockQty`) — this is the first point stock enters the system, via `incrementStock()` with `reason: initial_stock`.
- Admin can later restock (`incrementStock()`, `reason: restock`) or make manual corrections (`incrementStock()`/`decrementStock()`, `reason: adjustment`) — e.g. damaged goods, miscount.
- Admin can edit or delete products/variants.

### 1.3 Payment verification
- Admin panel has a **pending payments** view — orders where `payments.status = pending_verification`, showing the order details, amount, and uploaded screenshot.
- No push notification in this phase — admin checks this list manually (Telegram bot notification is a future enhancement, out of scope for now).
- Admin cross-checks the screenshot against their own bank/UPI statement, then confirms or rejects.
- **On confirm:** `payments.status → success`, `payments.verifiedBy` / `verifiedAt` set, `orders.paymentStatus → paid`, `orders.status → confirmed`, `decrementStock()` runs for each `order_item`, customer is notified.
- **On reject:** `payments.status → failed`, order stays unconfirmed; customer would need to retry payment/upload (exact retry UX is an open item).

### 1.4 Dashboard & insights
- Combined view across both channels: today's sales, order counts, low-stock alerts.
- Order management: view/filter website orders, update status, add manual tracking reference.
- POS sales log: view sales across staff/shifts.
- Inventory: combined stock view + full `inventory_logs` audit trail.
- Staff management: edit/deactivate staff, change roles.

## 2. Website Flow

### 2.1 First visit (guest)
- User visits rogueon.com for the first time — no Better Auth session exists.
- Backend generates a guest cookie (`guest_session_id`) and sets it — this is how the backend recognizes this visitor on future requests, including after a refresh.

### 2.2 Browsing
- Product listing/detail/category endpoints are public — no auth or guest cookie required just to browse (though the guest cookie will already be set from the first request regardless).

### 2.3 Cart
- User adds item(s) to cart → backend looks up (or creates) a `carts` row matching their `sessionId` (guest) or `userId` (logged in), and inserts/updates `cart_items`.
- Refreshing the page: cart persists, since the backend re-reads the same guest cookie or session, and looks up the same cart.
- If a guest later logs in: their guest cart (matched by `sessionId`) is merged into their account's cart (matched by `userId`) — no items lost.

### 2.4 Checkout
1. User clicks checkout. Frontend collects delivery details:
   - **Guest:** name, phone, full address, city — entered fresh, not saved.
   - **Logged-in:** select a saved `addresses` row, or add a new one.
2. `POST /checkout` — request includes the cart reference (guest `sessionId` or `userId` resolves it server-side) and either `shippingAddressId` (logged-in) or the guest address fields.
3. Backend, inside this request:
   - Validates stock is available for every item in the cart.
   - Snapshots each variant's current price into `order_items.price`.
   - Creates the `orders` row (`status: pending`, `paymentStatus: unpaid`) and `order_items` rows, from **the entire cart** (v1 has no partial-checkout — customer removes unwanted items from the cart first if they don't want everything).
   - Creates a `payments` row (`status: pending_verification`, `amount` = order total).
   - **No stock is deducted at this point.**
4. Response returns `orderId` and QR data (amount + static QR image reference).

### 2.5 Payment
5. Frontend displays the static QR and the amount due.
6. User scans the QR in their own banking/UPI app and pays externally — the backend has no visibility into this step happening.
7. User uploads a screenshot of their payment confirmation → `POST /payments/:orderId/proof` — file goes to S3/Cloudinary, `payments.screenshotUrl` is updated.
8. Order now sits waiting: `orders.status: pending`, `orders.paymentStatus: unpaid`, `payments.status: pending_verification`.

### 2.6 Verification → confirmation
9. Admin verifies manually (see Section 1.3). On confirmation, stock decrements, order status updates to `confirmed`, and the customer is notified (exact notification channel — email/in-app — TBD).

### 2.7 Post-purchase
- Logged-in customers can view order history and track status via `orders.status`.
- Guests have no account to view history against — order confirmation/tracking would need to be handled via the `orderNumber` + some lookup mechanism (e.g. a "track my order" page by order number + phone) if this is wanted — currently not explicitly scoped.

## 3. POS Flow

### 3.1 Staff login
- Cashier logs in via the same shared `/auth/login` endpoint — Better Auth session created, `role: cashier` (or `admin` if an admin is operating the POS).

### 3.2 Building a sale
- Cashier searches for a product by name or SKU (fast lookup, since SKU is unique per variant).
- Adds item(s) to the current sale ticket, with a live running total as items are added/removed.

### 3.3 Payment & completion
- Cashier selects payment method (cash, or QR if supported at the counter — per open item in the PRD).
- Sale is completed — unlike the website flow, **this is immediate and final**, no pending-verification step: `pos_sales` + `pos_sale_items` rows are created, and `decrementStock()` runs right away for each item, since the cashier has already confirmed payment was received in person.
- Receipt data is generated (print or digital).

### 3.4 Offline capability
- If the POS device has no connectivity: the sale is recorded locally in the browser's IndexedDB, stock is decremented **locally** on the device, and the sale is tagged `pending sync`.
- Once connectivity returns, queued sales are pushed to the backend in order.
- Backend commits each queued transaction through the same `decrementStock()` function used everywhere else, with row-level locking to prevent overselling.
- If overlapping offline sales pushed stock negative, the sale is still recorded and flagged for staff review rather than silently rejected.

### 3.5 Real-time sync
- On every stock-affecting event (website order confirmed, POS sale completed, admin restock), the backend emits a `stock.updated` event over WebSockets.
- Connected website sessions and other POS terminals receive it and reflect the new stock level immediately — no polling.

## 4. Where the Two Channels Actually Touch

| Shared concern | Website side | POS side |
|---|---|---|
| Auth | Customer login (`role: customer`) | Staff login (`role: cashier`/`admin`) — same Better Auth instance |
| Product catalog | Read for browsing | Read for SKU search |
| Stock | Deducted on **admin payment confirmation** | Deducted **immediately** on sale completion (or on offline sync) |
| Real-time updates | Receives `stock.updated` | Receives + can also trigger `stock.updated` |

Both channels ultimately call the same `incrementStock()` / `decrementStock()` functions and write to the same `inventory_logs` table — this is what keeps stock correct and in sync regardless of which channel a sale came from.
